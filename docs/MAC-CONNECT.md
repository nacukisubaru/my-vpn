# Подключение на macOS: 3 способа и почему GUI-клиенты падают

## Коротко

| Способ | Команда | Покрывает | Нужен sudo |
|---|---|---|---|
| **TUN (полный VPN)** | `sudo ./vpn-tun.sh` | ВСЁ: браузер, приложения, DNS | да |
| **Системный прокси** | `./vpn-browser.sh` | браузер + приложения, уважающие прокси | нет |
| **Только SOCKS** | `./connect-link.sh` | то, что вы направите на 127.0.0.1:1080 | нет |

Перед любым способом:

```bash
./vpn-doctor.sh          # покажет, что мешает
```

## Диагностика: почему браузер «не работает»

```bash
./vpn-doctor.sh
```

Скрипт проверяет:

1. **Запущенные VPN-клиенты.** Если их несколько (v2RayTun + Hiddify + Outline…),
   они дерутся за системный прокси и TUN. Оставить надо один.
2. **Залипшие системные прокси.** Частая беда: клиент выставил прокси на свой порт
   (у Hiddify это, например, `12334`), а потом умер/был закрыт. Прокси остаётся включённым,
   порт никто не слушает → **весь интернет в браузере «умирает»**, хотя Wi-Fi работает.
   Скрипт это подсвечивает как ⚠️.
3. Кто слушает локальные порты.
4. TUN-интерфейсы и маршрут по умолчанию.

Лечение залипших прокси:

```bash
./vpn-doctor.sh --clean
```

## Способ 1: TUN — настоящий VPN (рекомендую)

```bash
sudo ./vpn-tun.sh
```

- Работает через **sing-box** (`.tools/sing-box`), создаёт TUN-интерфейс.
- Весь трафик системы идёт через сервер, включая DNS.
- Не зависит от системного прокси — браузер работает сразу.
- Остановить: `Ctrl+C` или `sudo ./vpn-tun.sh --off`.

Проверка конфига без запуска (без sudo):

```bash
./vpn-tun.sh --check
```

Скрипт сам предупредит, если запущены другие VPN-клиенты.

## Способ 2: системный прокси (без sudo)

```bash
./vpn-browser.sh
```

- Поднимает Xray: SOCKS `127.0.0.1:1080` + HTTP `127.0.0.1:1081`.
- Ставит системные прокси **только на активный сетевой сервис** (Wi-Fi/Ethernet),
  а не на все — иначе конфликт с Outline/Hiddify/v2RayTun, у которых свои сервисы.
- По `Ctrl+C` выключает прокси и возвращает систему в исходное состояние.

Ограничения: не покрывает приложения, которые игнорируют системный прокси; DNS
резолвится локально (хотя сами запросы идут через туннель).

Если что-то зависло и интернет пропал:

```bash
./vpn-browser.sh --off
# или
./vpn-doctor.sh --clean
```

## Способ 3: только SOCKS (для проверки/скриптов)

```bash
./connect-link.sh
```

Поднимает SOCKS на `127.0.0.1:11080`, проверяет реальную передачу данных
(google/youtube/github с числом байт) и печатает лог соединений.
Ничего в системе не меняет.

Дополнительно:

```bash
./connect-link.sh --config client/config-import.json   # сохранить JSON-конфиг
```

Такой JSON импортируют Hiddify / v2rayN / NekoBox напрямую — это обход проблем
с парсингом `vless://` ссылок в GUI.

## Почему ссылка работает в моих тестах, а в клиентах нет

Проверено на этом же Mac: ссылка парсится стандартно, Xray с этими параметрами
скачивает 800+ КБ с YouTube. Значит дело не в ссылке и не в сервере.

Частые причины на стороне клиентов:

| Причина | Признак | Решение |
|---|---|---|
| **Mux включён** | подключается, но трафик не идёт | выключить Mux (Vision с ним несовместим) |
| **Залипший системный прокси** от прошлого клиента | браузер «нет интернета», Wi-Fi работает | `./vpn-doctor.sh --clean` |
| **Несколько клиентов одновременно** | нестабильно, то работает, то нет | оставить один |
| Старый профиль после ротации | «подключено», трафика нет | обновить подписку |
| Приложение не понимает `spx` / `support-x25519mlkem768` | ошибка импорта | минимальная ссылка или JSON-конфиг |
| IPv6 у клиента | долгий таймаут | принудительно IPv4 |

## Минимальная ссылка (без необязательных параметров)

```
vless://<UUID>@82.148.226.31:443?type=tcp&security=reality&encryption=none&pbk=<PBK>&sid=<SID>&sni=<SNI>&fp=chrome&flow=xtls-rprx-vision#vpn
```

Актуальные значения — в `client/vless-minimal.txt`. Проверено: работает без `spx`
и без пост-квантового параметра.
